# Configuration

Read this when you change `config.json`, or when a setting below explains what `dispatch`, `review` or `escalate` did. [SKILL.md](../SKILL.md) has the roles and the rules.

Personal settings live in `config.json` in the ledger home; every key is optional:

```json
{"lang": "zh",
 "fable": true,
 "worker": {"kind": "codex", "model": "<model>", "effort": "high"},
 "reviewer": {"kind": "claude", "model": "<model>"},
 "profiles": {"hard": {"kind": "claude", "model": "opus", "effort": "xhigh", "advisor": "fable"}},
 "review": {"standard": "fable", "light": {"model": "opus", "effort": "high"}},
 "pm": {"kind": "claude", "model": "opus", "narrow_tools": true, "lean": true},
 "agents": {"mine": {"argv": ["mine", "--yes"], "model": ["--model", "{}"], "effort": [], "prompt_arg": false}},
 "codex": {"args": ["-c", "model_provider=\"<name>\""], "model_prefix": "<prefix>/"},
 "memory": {"native": true,
            "dream": {"auto": false, "profile": "light", "min_hours": 24, "min_new": 8,
                      "max_wait_days": 7, "timeout": 900}},
 "discord": false}
```

`codex` (`args`, `model_prefix`) and `discord` are described in [herdr-tui.md](herdr-tui.md); the rest of `codex`, and `claude`, `hc`, `tabs`, `workers` and `deep`, under Launch policy and Deep below.

`lang` is the language of built-in text (the handover prompt, recorded quotes, dashboard labels): `en` by default, or `zh`. `worker` gives the defaults for `pm.py dispatch`; its `--kind`, `--model` and `--effort` flags win, and without either the worker program's own defaults apply. `profiles` replaces or adds the worker profiles that `dispatch --profile` and `escalate` name (built in: light, standard, hard, deep; `worker` may name one as `"profile"`). `review` changes the review table, which picks the reviewer's model from the profile the task's worker ran with. `fable` (default `true`): set it to `false` where Fable cannot be used (Bedrock, Vertex, a gateway, an account without it); hard then runs without the advisor, deep is not offered and escalation ends at hard, and the review table's Fable entries go to Sonnet. What `profiles` and `review` say still wins. Any Claude worker or reviewer that runs on Fable is started with `--fallback-model` (worker: opus, reviewer: sonnet), and its note says so. `reviewer` gives the defaults for `pm.py review` instead of that table, and falls back to `worker`. `pm` gives the defaults for `pm.py start` and `rotate`; a Claude Code PM runs on `opus` unless `pm.model` or `--model` says otherwise. `pm.py start` and `rotate` start a Claude Code PM with `--disallowedTools Edit,NotebookEdit` so it changes no files itself (`"narrow_tools": false` turns that off), and pass `--settings pm-settings.json` from the ledger home with guided compaction (`autoCompactWindow: 200000`, `idleCompaction: true`, `env.CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS: "150000"`). They also start Claude Code lean, since every turn re-reads the whole context (`--strict-mcp-config --no-chrome`, plugins off, user skills user-invocable only); `"lean": false` turns lean flags off while keeping compaction and memory settings. Codex PM starts with `-c model_auto_compact_token_limit=220000`, `model_post_turn_compact_threshold_percent=80`, and `compact_prompt`, and pi PM loads `-e .../pm_pi_compact.js`. `memory` configures the memory adapters and background consolidation (`autoDream`): every agent gets the memory index in its handover or brief and writes with `pm.py remember`; Claude Code is also started with its own memory (`autoMemoryDirectory`, in the same `--settings` file) pointed at the project's memory folder (the PM) or at a folder of candidates (a worker), once the project has a memory, and `{"memory": {"native": false}}` turns that pointing off. `memory.dream` configures background consolidation of eligible project memories (`pitfall` and `reference` written by workers/helpers/dream) and idle worker candidates: `auto` (default `false`) lets the project deliverer trigger `pm.py dream run --auto` when the PM turn is idle (manual `pm.py dream run` ignores it; automatic triggering pauses after 3 consecutive failures until a manual run succeeds); `profile` (default `"light"`) sets the read-only dream helper's profile (profiles that ask the user first, such as `deep`, are refused); `min_hours` (default `24`) is the minimum cooldown between automatic attempts; `min_new` (default `8`) is the minimum count of new/updated eligible memories plus unseen candidates needed to trigger automatically; `max_wait_days` (default `7`) triggers automatically once the oldest pending item has waited that many days even below `min_new`; `timeout` (default `900` seconds) is the helper timeout. Non-positive or non-numeric values fall back to the defaults.

**Any coding agent can be the PM or a worker.** `kind` names the program: `claude`, `codex`, `pi`, `gemini` and `opencode` are built in; `agents` adds others or overrides a built-in one. `argv` is the command, `model` and `effort` are the flags that carry those values (`{}` is replaced), and `prompt_arg` says the program takes its first prompt as a trailing argument; without it the prompt is typed in once the program is ready. A kind that is not listed is run as written (`--kind "mine --yes"`). What differs between agents: Claude Code and Codex wire `SessionStart` (including `compact` re-sync), `PreCompact` (`pm.py hook-pre-compact`: plain-text instructions for Claude, JSON `systemMessage` for Codex), `PreToolUse` (`pm.py hook-pre-tool`: intercepts PM interactive user-question tools such as `AskUserQuestion` / `request_user_input` and redirects them to ledger question cards), `UserPromptSubmit`, and `Stop` hooks (pi uses `pm_pi_compact.js`); `agy` has no `PreCompact` hook or configurable auto-compaction threshold, so a long `agy` PM session rotates manually when needed. Context usage display and compaction-boundary `postTokens` are read from Claude Code transcripts. Everything else (ledger, dispatch, review, swap, board) is the same for all.

**Windows.** The command lines `pm.py` writes (the report lines in briefs, the handover command, the "send it by hand" lines) name the script as `py -3 "C:/…/pm.py"` (else the quoted interpreter path), with paths in double quotes and forward slashes, which cmd, PowerShell and Git Bash read alike; a ledger home other than the default goes in as `pm.py --home "<dir>" <command>` instead of `PM_HOME=…`. `codex-cmd` prints a line for PowerShell. `land` ends a check that runs out of time with `taskkill /T /F`. A `reattach` lock counts as stale only by its age there (five minutes): whether the process that holds it is still running is not checked.

## Launch policy

How workers are started and closed in the desktop app (`dispatch`, `review`, `escalate`, `reattach`, `codex-cmd`, `update`). Every key is optional, everything here is off until you set it, and none has a machine-specific default: copy the shape below and fill in your own values.

```json
{"codex": {"profiles": [{"name": "<profile-a>", "max": 2, "fast": true}, {"name": "<profile-b>", "max": 3}],
           "projects": ["<project folder name>"], "allow_default": false,
           "model": "<model>", "review_model": "<model>", "effort": "high",
           "fallback": {"worker": {"kind": "claude", "model": "opus"},
                        "reviewer": {"kind": "claude", "model": "fable"}}},
 "claude": {"launcher": ["zsh", "-ic", "<your claude command> {args}"], "effort": "high", "fable_fallback": "opus"},
 "hc": "<path to hc>",
 "tabs": {"new_tab": false, "max": 20, "review": "review", "bug_pattern": "#?([0-9]{5})", "rename_via_core": false},
 "workers": {"close_on_close": false, "close_reported": false, "idle_minutes": 30},
 "helpers": {"profile": "opus", "max": 3, "project_max": 10, "timeout": 1800},
 "deep": {"confirmed": false}}
```

- **Codex profile pool.** `codex.profiles` lists the codex profiles (`codex -p <name>`) workers run on, tried in order; each `max` counts the codex sessions running now in this project's folders (its checkout and worktrees, whatever started them; a session started with `-c model_provider="<name>"` counts too, and `providers` lists other names a profile counts under). The first under its max is used. Sessions are counted from `/proc`, so on Linux only: elsewhere nothing is counted and the dispatch note says so. `allow_default` (default `false` once profiles are listed): codex never runs on its default provider (no `-p`), and `--codex-profile default` is refused. All full: the worker runs on `fallback.worker` (a reviewer on `fallback.reviewer`) instead, and the output and the task log say why; without `fallback`, a worker gets the built-in standard profile (Claude Opus) and a reviewer the review table's standard entry (Fable; Sonnet with `"fable": false`). A Fable fallback still asks the user first (Deep, below). `--codex-profile <name>` picks one (a full one with a warning). `projects`: only these project folder names use the pool (default: every project); other PMs keep their own codex args. Within the pool the PM's `codex.args` lose `model_provider` and `service_tier`; `~/.codex/config.toml` is never changed. `model`, `review_model` and `effort` fill what the command line and `worker`/`reviewer` leave open. A dispatch holds `locks/codex-pool-<project>.lock` in the ledger home from the count until its session shows, so two dispatches do not take the same slot. `"fast": true`: once the session is up, `/fast` is sent, unless its status line already says `fast` (`/fast` toggles; `ultrafast` is not fast); the line is read again and the task log records it. The default provider never gets fast. The worker's `worker` record keeps the profile (`provider`), and `reattach` resumes it on the same one.
- **Launchers.** `claude.launcher` is how a Claude worker or reviewer is started in a herdr-core terminal, for a machine where a plain `claude` cannot start there (for example a login that only an interactive shell sets up). `{args}` is the rest of the command line (model, effort, `--fallback-model`, `--settings`), quoted for the shell; without `{args}` they are added at the end. `codex.launcher` works the same way. None by default; the herdr TUI starts the kind's own program and uses no launcher. A program started this way may report no status to herdr-core; its brief is then sent once its screen shows its input (Claude Code's `? for shortcuts` or `bypass permissions` line, codex's `Ask Codex`). `claude.effort`: a Claude worker's or reviewer's effort when nothing else names one. `claude.fable_fallback`: the `--fallback-model` of every Claude worker or reviewer on Fable, instead of opus (worker) and sonnet (reviewer). `hc`: the path of herdr-core's CLI where it is on an interactive shell's PATH only (default: `hc` from PATH).
- **Worker tabs.** By default a worker is a sub-agent row under its PM's terminal, so the app shows which PM it belongs to. `tabs.new_tab: true` gives each worker a tab of its own in the PM's space instead, named `<terminal>-<BUG>-<short>` once its terminal is made, and the task's ledger `agent` is set to the same name: `t5g-12345-login-fix`; without a BUG number `<terminal>-<short>`: `t5m-review-login-fix`. `<terminal>` is the herdr-core address (`hc:t5g` → `t5g`). The BUG number is `--bug`, else what `tabs.bug_pattern` (a regular expression; its first group) finds in `--tab`, else in the title; without a pattern only `--bug` sets it. It is taken out of `<short>` and put after the address; a `--tab` that starts with an address (`t5g-…`) gets the new terminal's in its place. `<short>` is `--tab` (default: the title), at most `tabs.max` characters (20); a reviewer's is `<tabs.review>-<the task's short>` (`tabs.review` default: review, or 审查 with `"lang": "zh"`). `escalate` and `reattach` name the new terminal the same way. When a worker or reviewer is given another task (a reviewer that reviews another branch), rename it in the same step: `pm.py retab <task id|t5m> --tab <new short> [--bug <N>]` renames the tab and sets the task's `agent` and `tab` (`--dry-run` prints the name only). The hc terminal name (`--name`) stays a-z 0-9 - _. Every worker terminal is labelled `task=<id>` and, with a parent task, `parent=`/`category=`. Where `herdr-app` is not installed (herdr-core on this machine, the app on another), tabs keep the app's names and the task log says so; `tabs.rename_via_core: true` renames them in the app's document in herdr-core instead, through `hc connect` (it reads and writes the whole document, and that protocol is not in Herdr's documented API, so it is off by default). It renames a PM's `PM-<project>` tab the same way.
- **Dispatch options.** `dispatch --task <id>` takes up an open task registered with `new` (its title, parent and branch); it refuses a task of another project, and one whose worker still runs (other than the session that only handed it to the PM). `dispatch --here` makes no worktree: the worker works in the project's checkout (or `--path`), so `--branch` is not needed (desktop app only). `--label` and `--name` default to the task id or title. `--dry-run` (also on `review` and `escalate`) prints the plan as JSON (profile, pool usage, argv, cwd, tab, fast, whether the user is asked first) and starts, makes and registers nothing.
- **Closing workers.** With `workers.close_on_close: true` (default off: a reviewer stays until its task is merged or retired, as before), when a task becomes done, merged, released or abandoned through `update`, its worker terminal is ended (`update --keep` keeps it): only a terminal pm.py started for that task (`dispatch`, `review`, `escalate`) and still labelled with it, never a PM's or a session that registered its own work, not while another open task uses it, and not in the middle of a turn. A worker or reviewer that closes its own task is ended once that turn is over (`close-worker`, in the background, after 20 s idle). `retire` of a `dispatch --here` task ends its worker's terminal whatever this says, as `retire` ends a worktree's. `workers.close_reported` (default off): a worker that reports with `--status review` from its own terminal is ended once it has been idle for `workers.idle_minutes` (30) while the task is still in review (sent back, or blocked on a question, it is left alone), and the task stays in review; it then shows as offline, and `pm.py reattach <id>` resumes its session when findings go back to it. `pm.py idle-workers [--minutes N] [--exited] [--close [<t> ...]] [--json]` lists this project's worker terminals idle or done for N minutes (default `workers.idle_minutes`) with their task; `--close` ends the ones named, or without names those whose task has reported or is closed (review, done, merged, released, abandoned): an idle worker of a task in progress or blocked may be waiting for an answer. A terminal hc reports no status for is listed as `no-status` and ended only when named. `pm.py status` lists reported tasks whose worker terminal is still open.
- **Helpers.** `helpers.profile` sets the default profile for `pm.py helper start` (default: `opus`, else `neon` when present in `profiles`, else built-in `light`; CLI `--profile`/`--kind`/`--model` win). `helpers.max` (default `3`): concurrent helpers per caller (PM or worker). `helpers.project_max` (default `10`): concurrent active threads plus running helpers across the project. `helpers.timeout` (default `1800` seconds, 30 min): default timeout per helper, enforced opportunistically by helper commands, `pm.py status` and `pm.py deliver`. A helper cannot start another helper (max depth 1). Helpers are read-only by default; only the PM may pass `--exec` (for delegated installs, approved merges via `pm.py approve --via helper`, or screen triage via `pm.py triage`) and `--async` for immediate non-blocking return.

## Deep (Fable) pre-approval

A Fable worker (deep, or any Fable model) asks the user first: `dispatch` and `escalate` block the task with a question card until they run again with `--confirmed`. `"deep": {"confirmed": true}` says the user has agreed to Fable workers for good, and `"confirmed": ["<project folder name>", ...]` says so for those projects only; then nothing is asked, and the dispatch or escalation note says `Fable pre-approved by the user (config.json deep.confirmed)`. Off by default. Set it only when the user says Fable is fine from now on, not for one task, and record that with `pm.py decide`. Never switch a task to another profile or model to get past the question: whether hard is used instead is the user's answer.
