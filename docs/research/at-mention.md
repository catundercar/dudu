# Designing `@` Mentions in the Input Box — Lessons from Cursor

> **Background**: This report examines the semantics and interaction design for `@` mentions in dudu's main project input box: when a user `@`-mentions a thread, document, or file, who receives the message, which objects belong in the menu, and how selections are rendered and serialized. Written in November 2026, drawing on behavior observed in released builds of Cursor 3.x (Agents Window and Projects) alongside Cursor's official documentation, API reference, and engineering blog.
> Written as a design proposal and subsequently approved: **`@` is a typed reference pointer while the message still goes to the manager**; the menu covers **three categories (`Threads`, `Library`, `Files`)**; and selected items render as **inline chips** inside the input box and sent message bubbles.

---

## Core Takeaways

1. **In Cursor, `@` is a typed context pointer, never a message router.**
   Whether you `@`-mention a file, a `Canvas`, a project `Task`, a running worker session (`Chat`), another `Project`, or a multiplayer teammate, pressing send always delivers the message to **the session that owns the current input box** (in the main Project view, the coordinator). The `@`-mentioned object enters that turn's context as a human-readable label paired with an exact ID or path, leaving the coordinator to decide whether to read its output or invoke a tool to steer the corresponding worker.
2. **Referring to an object and talking directly to a worker are separated spatially.**
   In Cursor Projects, bypassing the coordinator to talk straight to a worker means opening that worker's own chat panel and typing in its input box. dudu's `mods/pm-project` already has that exact per-thread input box (`say-thread`) at the bottom of the right-hand thread detail pane. Typing `@some-thread` in the main project input box always means talking to the manager *about* that thread — covering both `"dispatch follow-up work based on @research-a"` and `"tell @impl-b to cover the edge cases too"`.
3. **dudu's choice: main-box `@` messages still go to the manager, with `@` acting as an ID-carrying reference pointer.** Routing messages directly into an `@`-mentioned worker's terminal creates structural failures (see §2.2), and adding a mode toggle would give the exact same visual chip two incompatible side effects.
4. **Recommended design**:
   - **Three categories**: `Threads` (merging ledger threads and standalone project sessions — in dudu a task and its worker session are naturally 1:1, so splitting `Chats` from `Tasks` like Cursor is unnecessary), `Library` (project docs, research reports, memories), and `Files` (repository files and folders).
   - **Two-level menu + top-level quick picks + instant cross-category search**: typing `@` alone shows the three category entries above a divider and the most active threads plus recent docs flat below it; typing characters immediately searches across all three categories; `Esc` steps back from a category submenu to level 1, and from level 1 closes the popup while keeping the draft intact.
   - **Inline chips + canonical plain-text link serialization**: render atomic chips via Herdr `gpui-kit`'s inline token API while serializing the underlying text as `[@Title](thread:<id>)`, `[@Title](library:<root>/<path>)`, or `[@path](file:<path>)`. Never inline full documents or long logs into the manager's context; render sent links as clickable chips in both user bubbles and manager replies.

## 1. How `@` Works in Cursor (Interaction and Mechanism)

### 1.1 Why the Top-Level Menu Leads with `Chats`, `Canvas`, and `Tasks`

In Cursor 3.x's Agents Window (and the Project coordinator view), when `@` has just been typed with no filter text yet, the observed menu has two sections:

1. **Upper section — category entries**, which drill into a submenu rather than closing the popup. In a Project session, the observed top-level categories are:
   - **`Chats >`**: past and active Agent sessions, including worker sessions spawned by the coordinator, plus cross-project references.
   - **`Canvas >`**: interactive visual canvases generated by Agents.
   - **`Tasks >`**: entries on the Project task board.
2. **Lower section — high-frequency quick picks**, primarily recently used **Files & Folders** and connected **MCP Servers** (categories documented in Cursor's official Prompting guide).

> **Division of labor across trigger symbols, and the removal of `@Docs`**
> - **`/`**: invokes one-shot Skills, pins a Skill as a persistent mode (`Option+Enter`), or triggers action commands (spawning cloud subagents, switching models, etc.). Inside a Project coordinator chat, modes are narrowed down to `Plan`.
> - **`#`**: links GitHub Issues and PR numbers (e.g. `#123`).
> - **`@Docs` was removed.** Cursor's official Release Notes explain: *"Removed non-working Docs options. The Docs category and Add New Custom Docs option had already stopped adding documentation to agent context, so they're gone from the @ mentions menu."* Cursor shifted instead toward filesystem- and Agent Store-based dynamic context discovery.

### 1.2 How Each `@` Category Enters Model Context

| Category | How it enters model context | Who receives the message |
| --- | --- | --- |
| **Chats** (worker sessions / past chats / Side Chats) | Never inlines the full transcript; passes only the session title and ID. Local chat transcripts live on disk for on-demand lookup (matching the "chat history as files" pattern in Cursor's *Dynamic Context Discovery* blog post); cloud/Project worker sessions pass a structured handle so the server exposes a summary/handle to the current Agent. | **Only the Agent owning the current input box** (e.g. the Project coordinator), never sent directly to the `@`-mentioned session. The coordinator decides whether to read its progress or steer it. |
| **Projects** (cross-project reference) | Same shape as a cloud Chat: `@<ProjectName>` paired with the target Project's coordinator ID. | Current coordinator only, as cross-project context. |
| **Teammates** (multiplayer Project members) | `@<Name>` paired with that teammate's coordinator session reference in the Project. | Current user's coordinator first; if the coordinator initiates a cross-user query, it lands in a forked **Side Chat** marked as untrusted agent input without interrupting the teammate's main chat (official Projects docs). |
| **Canvas** | Structured artifact reference carrying the canvas ID so the Agent can read or update it in place. | Current Agent. |
| **Tasks** (Project board items) | Passes only task ID and title rather than copying long task descriptions; the coordinator looks up the item on the shared task board/notes. | Current coordinator, never sent straight to the worker behind the task. |
| **Files & Folders** | `@<relative-path>`; short code selections are inlined, while whole files pass only the path for on-demand reading (also triggering path-glob `.mdc` rules). | Current Agent, pure context injection. |
| **Agent Store** (shared project store & personal store) | Official docs: Projects mount two persistent directories on every machine — the shared project store (`Context` in UI, `/cursor/stores/self`) and the personal store (`/cursor/stores/user`, carried across projects). Both are real files read and written directly by Agents. | Current Agent. |
| **Terminals** | Integrated terminal output is synced to local files so the Agent greps error lines on demand rather than stuffing full scrollback into the prompt (*Dynamic Context Discovery*). | Current Agent. |
| **Git** (`@Branch` / `@Commit` / PR Diff) | Injected as diff/commit references with line-level truncation on large diffs. | Current Agent. |
| **Browser / MCP / Rules** | Browser page snapshot references, MCP tool catalogs, or explicit rule references. | Current Agent. |

Unifying invariant: **`@` only adds a pointer to the turn's context; it never changes who the message is addressed to.**

### 1.3 Coordinator–Worker Communication Boundaries in Cursor Projects

Per the Cloud Agents API reference and Projects documentation / best-practice guides:

1. **The Project ID *is* the root coordinator's Agent ID**: creating a Project (`POST /v1/projects`) returns `project.id === coordinatorAgentId`. There is no separate "chatroom router" layer — every message sent in the main Project view calls `POST /v1/agents/{coordinatorAgentId}/runs`.
2. **Follow-up vs. steer when busy**: each Agent runs at most one active turn at a time. While busy, an ordinary follow-up returns `409 agent_busy`; passing `delivery: "steer"` injects the message at the next safe step inside the running turn (`202 { delivery: "steered" }`), or queues it (`{ delivery: "queued" }`) if the turn just finished.
3. **Two kinds of executors**:
   - **Standalone worker Agents** (listed via `GET /v1/projects/{id}/agents`): opening a worker's own chat view lets you follow-up or steer it directly, whereas `@`-mentioning it in the coordinator's chat box simply hands a reference to the coordinator. Cursor's Projects guide emphasizes strict steer discipline: *"One steer per worker per topic. Never a burst. Why: steers queue behind the running turn and the worker stalls."*
   - **Lightweight internal subagents**: driven strictly by their parent Agent; external follow-up/steer calls are rejected with `400 validation_error: "Follow-ups and steers to subagents are not supported. Send them to the parent agent."`

### 1.4 Menu Interaction, Keyboard, and Chip Rendering (Observed Behavior in Released Versions)

1. **Trigger**: typing `@` at the start of a line or after whitespace opens the popup; deleting `@` dismisses it.
2. **Browse vs. search mode**: with nothing typed after `@`, the menu browses by category and supports stepping back out of a category; selecting a folder drills into its children (documented in the Prompting guide). Typing characters immediately switches to a flat cross-category search.
3. **Keyboard**: `↑` / `↓` move selection, `Enter` / `Tab` activate the highlighted row, and **`Esc` steps back one layer at a time**: from a category submenu back to level 1, and from level 1 closing the popup while leaving typed text intact (Release Notes document `Escape` dismissing popups one layer at a time).
4. **Display**: chosen items appear as inline chips (icon + label) inside the input box; once sent, user messages in the timeline likewise render clickable chips that open the referenced file, canvas, chat, or task.

## 2. Implications for dudu: `@` Semantics and Data Sources

### 2.1 Why `@` Should Be a Reference Pointer Rather Than a Cross-Session Router

Every message sent in a project conversation has two orthogonal dimensions:

- **Addressing** (who is being spoken to): determines whose session wakes up, interprets intent, and owns state transitions.
- **Reference** (what is being talked about): disambiguates natural language (which of three past "icon" tasks? which spec in Library? which `main.js`?) by handing an exact identifier to the recipient.

Comparing Cursor Projects with dudu's own mechanics:

| Dimension | Cursor Projects | dudu | Constraint on `@` design |
| --- | --- | --- | --- |
| **Conversation source of truth & coordinator lifetime** | Root coordinator Agent; auto-summarizes when full, archiving history as searchable files | `projects/<slug>/conversation.jsonl` on disk; manager session hands over or compacts when context grows | Any change in task direction must pass through the manager and ledger (`log` / `brief`), or future reviews and handovers lose the updated requirements. |
| **Talking directly to a single worker** | Click into a worker's own chat panel | Open the thread in the right-hand `Threads` pane and use `say-thread` at the bottom (sends straight to that worker's terminal), or focus its terminal | **A spatially separate direct channel already exists**; overloading main-box `@` as a hidden second direct pipe is redundant and confusing. |
| **How the coordinator drives a new worker turn** | Coordinator calls a single steer tool call (one steer per worker per topic) | Manager runs one atomic command: `pm.py update <id> --status in_progress --note "..." --send` (logs to ledger, flips status back to `in_progress`, records turn baseline, and types into terminal) | **Hard constraint**: `pm.py`'s stall detector watches only `status == "in_progress"` tasks. Typing directly into a `review` or `blocked` worker without updating the ledger leaves the task in its old status with a stale turn counter, **completely missing stalls or crashes**. The manager playbook explicitly forbids splitting status updates from message sending. |
| **Offline or finished threads** | Archived Cloud Agents auto-resume server-side on follow-up | Exited threads sit at `offline` (or `merged` / `done`) and require `pm.py reattach <id>` or reading historical reports | Direct terminal routing fails outright on offline or merged threads; sending to the manager lets it either read past findings or `reattach` first. |
| **Coordinator context budget** | Dynamic Context Discovery: pass path/ID pointers, never inline big files or full chat logs | Lean manager session rule: measurements showed a large share of manager tokens wasted reading raw files/diffs directly instead of delegating to workers/helpers | dudu's `@` must likewise **never paste full document bodies or thread logs into the prompt**, passing only a readable label + exact ID/path. |

### 2.2 Evaluating Three Semantic Options

Starting from an IM group-chat `@Bot` mental model initially suggested three options:

1. Route directly to the `@`-mentioned agent: `@thread` sends text straight into that worker's terminal while logging a note for the manager;
2. Send to the manager as usual, treating `@` as a structured reference for the manager to read or forward;
3. Support both via a toggle (direct send by default, switchable to via-manager).

**Decision: Option 2, elevating "naming" into a structured reference pointer.**

Why Option 1 fails:

1. **In natural language, `@` is frequently a direct/indirect object rather than the addressee.** Saying `"Based on the findings in @at-mention-research and @spec-worker-alerts.md, dispatch someone to build the UI"` asks the manager to spawn new work — typing that sentence into a finished research worker's terminal makes zero sense. Treating `@` as direct routing breaks cross-thread synthesis and prevents `@Threads`, `@Library`, and `@Files` from sharing a uniform grammar.
2. **Multiple `@` mentions become undecidable**: `"Have @thread-a and @thread-b align on field names"` or mixing `@thread` + `@doc` has no single target terminal.
3. **Breaks stall detection**: see §2.1; blindly injecting text into a busy worker can also interrupt running verification suites.
4. **Fails on offline and merged threads**, which have no live terminal.
5. **The IM group-chat analogy is backwards**: group-chat bots are peers with no coordinator, whereas dudu's project view (like Cursor Projects) is a 1:1 control room between you and the project manager, with workers as execution branches underneath. Direct 1:1 worker chat already lives inside `say-thread`.

Why Option 2 works cleanly:

- **One consistent grammar everywhere**: `@Thread`, `@Library doc`, and `@File` all mean "hand an exact pointer to the session owning this input box" — the manager in `say`, or that thread's worker in `say-thread`.
- **Covers both intents**: `"Use @thread-a to do X"` lets the manager read A's report and dispatch X; `"@thread-a change the border radius to 8px"` gives the manager the exact task ID to run `pm.py update <id> --status in_progress --note "..." --send` atomically (reattaching first if offline).

Why Option 3 is rejected: giving identical `@name` chips two opposite execution targets depending on a toggle undermines UI predictability and clutters the minimal icon-based input bar.

### 2.3 Category Design and Data Source Audit

| Candidate category | What it maps to in dudu | Serialization & meaning | Current data source readiness | Verdict |
| --- | --- | --- | --- | --- |
| **Threads** (maps to Cursor's `Chats` + `Tasks`) | In dudu, **one thread naturally unifies ledger task + git branch + worker terminal**. Includes: (1) active threads (`waiting` / `review` / `working` / `offline` / `paused`, with review sub-threads folded); (2) unregistered standalone sessions in the same repo/worktree (helpers, manually launched agents); (3) recently finished threads (`merged` / `done` / `released`, excluding `abandoned`). Excludes the manager itself in `say`. | Ledger thread: `[@<Title>](thread:<task-id>)`; standalone session: `[@<Name>](session:<terminal>)`. Never inlines logs. Manager resolves `thread:<id>` unambiguously (`pm.py show` / `update --send` / `reattach`). | **Ready today**: `pm.py state` plus Herdr's terminal/agent list already gives `mods/pm-project/model.js` active threads, standalone sessions, and ended threads (including remote machines). | Ship in v1 |
| **Library** (maps to Cursor's Agent Store / `Context` + `Canvas`) | Shares the exact information architecture of the Library / Memory design: (1) project docs (`docs` root, e.g. specs, filtering out handover/verify/candidate scratch files); (2) research reports (`research` root, `<repo>/evidence/<topic>/README.md`); (3) memory entries (project & personal, letting users say `"update/forget @some-memory"` or `"follow @some-rule"`). | `[@<Doc Title>](library:<root>/<path>)`, never inlining body text. | **Files** (maps to Cursor's Files & Folders) | Tracked and untracked non-ignored files/folders in the project repo (`.gitignore`-aware). | **Git branches / commits** | Unmanaged branches or historical commits | `branch:<name>` or commit SHA | Active branches are already 1:1 with `@Threads`, and managers do not review loose commits directly; no commit search endpoint exists yet. | Defer |
| **Individual chat messages / question cards** | Past lines in `conversation.jsonl` or open question cards | Question cards already have dedicated reply binding ("Answer in your own words" pins a banner above the input and prefixes the reply); text-searching individual chat bubbles via `@` is awkward (Cursor omits it too). | Add hover "quote reply" on bubbles later if needed rather than putting chat lines in `@`. | Exclude |

## 3. Recommended Design

### 3.1 Menu Hierarchy and Candidate Layout

Both the main project input (`say`) and the per-thread detail input (`say-thread`) share the same `@` menu component (in `say-thread`, the current thread itself can be dimmed or omitted while all other threads, Library items, and files remain available).

**(1) Trigger conditions**

- The cursor immediately follows a newly typed `@` placed at the start of the text or right after whitespace or punctuation (`foo@bar` does not trigger).
- There is no newline between that `@` and the cursor, and that `@` offset has not been dismissed via `Esc`.

**(2) Level 1 (just typed `@`, empty query)**

Anchor a `gpui-kit` `Popup` at `top_left` above the input box (rounded card, soft shadow, ~300px max height with scroll), split into two sections:

```text
┌──────────────────────────────────────────────────────┐
│  [hook]    Threads                             6   > │
│  [context] Library                            18   > │
│  [file]    Files                                   > │
├──────────────────────────────────────────────────────┤
│  ● @-mention input design                   waiting  │  ← flat active items below divider, pick with zero drill-down
│  ⋯ Research: what belongs in Library        working  │
│  ● Context usage UI                          review  │
│  📄 spec-worker-alerts.md               project doc  │
└──────────────────────────────────────────────────────┘
```

- **Upper section** (category entries with item counts and `>`): clicking or pressing `Enter` / `→` drills into level 2 while keeping the popup open.
- **Lower section** (quick picks, up to 6 rows): up to 4 active threads in the project (ordered `waiting` > `review` > `working`) plus the 2 most recently modified Library documents. In a project with three or four active threads, `@` + `↓` + `Enter` selects one immediately with single-level speed, while larger projects stay organized behind categories.

**(3) Level 2 (inside `Threads` / `Library` / `Files`)**

- Pin **`← Back`** as the top row with the current category title on the right; clicking it or pressing `Esc` returns to level 1.
- If filter characters were typed before entering a category, clear them upon entering so the full category list is visible; subsequent typing filters within that category only.
- Row presentation:
  - **Threads**: matches the right-hand `Threads` pane (status dot / pulsing indicator + title + agent badge); `offline` threads appear muted ("Disconnected") yet **remain selectable**; ended threads fold into a collapsible footer section.
  - **Library**: grouped under Project Docs / Research Reports / Memories, showing an icon or type dot + title + short description.
  - **Files**: file/folder icon + relative path; selecting a folder row or typing `/` drills down inside the popup, whereas selecting a file inserts the chip and closes the popup.

**(4) Global search mode (typing right after `@`, e.g. `@cursor`, `@main.js`)**

- Hide category headers and **rank matches flat across all three categories** (capped around 30 scrollable rows).
- Matched fields: thread title / task ID / branch name; Library title / path / memory slug; repository relative path and basename.
- Ranking: exact prefix match > title/basename substring > path/description substring; ties broken by active threads > Library docs > repo files > ended threads.

### 3.2 Keyboard Handling and the `Esc` Stack

1. **Key interception while the popup is open** (handled before the input's `Enter`-to-send binding):
   - `↑` / `↓`: move across selectable rows (skipping group headers) and scroll the highlighted row into view.
   - `Enter` / `Tab` (without `Shift`): suppress form submission. On a category or folder row, drill down; on `← Back`, return to level 1; on a leaf item, insert the token chip and close the popup.
   - `→` (empty query, category row highlighted) enters the category; `←` (empty query, inside level 2) returns to level 1.
2. **`Esc` steps back strictly one layer at a time**, sitting at the top of `mods/pm-project/model.js`'s existing `Esc` priority stack:

   ```text
   1. mentionSubmenuOpen  → return to @ menu level 1 (popup stays open, draft preserved)
   2. mentionMenuOpen     → close @ menu (record dismissed offset, keep draft & focus)
   3. answering           → detach "Answer in your own words" question-card banner (draft preserved)
   4. typing              → blur input when non-empty draft is focused (draft preserved)
   5. search              → clear/close Library search or in-document find
   6. detail              → close right-hand thread detail back to thread list
   7. doc                 → close right-hand document view back to document list
   8. listOpen            → collapse slide-over sidebar in narrow windows
   ```

### 3.3 Input and Message Bubble Rendering

**(1) Foundation: native inline tokens in `gpui-kit`**

Inspecting Herdr's `gpui-kit` type definitions confirms that `TextareaState` and `Textarea` (already used by `pm-project`) provide atomic inline token chips out of the box:

- `state.replace_range_with_token(range, { id, text, label })`: atomically replaces `[atPos, cursorPos]` with an inline token that deletes as a single unit on Backspace and prevents the caret from splitting the label.
- `Textarea.new(state).token((ctx, cx) => Element)`: custom-renders chip visuals (small icon + label, rounded pill background, highlighted border when selected) and supports `.on_token_click` / `.on_token_hover`.
- `state.content()` returns `{ text, tokens }` and `state.set_value(...)` restores both text and tokens together, so local draft persistence only needs an optional `tokens` array to survive mod reloads and project switches.
- `state.value()` returns the plain string with each `token.text` spliced in.

> [!NOTE]
> Because no mod in the repository has exercised `Textarea.token()` in a live window yet, implementation should verify multi-line auto-grow and CJK IME composition alongside inline tokens first, falling back to `Textarea`'s default built-in token styling if any quirk appears.

**(2) Plain-text serialization: self-contained and backward-compatible**

Keep each chip's visual `label` concise while serializing `token.text` as standard Markdown link syntax extending dudu's existing `thread:<id>` convention:

| Object kind | Chip display | Underlying `token.text` (written to terminal & `conversation.jsonl`) |
| --- | --- | --- |
| Ledger thread | `[status dot] Research: @-mention input design` | `[@Research: @-mention input design](thread:<task-id>)` |
| Standalone session | `[agent] helper-1` | `[@helper-1](session:<terminal>)` |
| Library doc / report / memory | `[context] spec-worker-alerts.md` | `[@spec-worker-alerts.md](library:project/spec-worker-alerts.md)` |
| Repository file | `[file] mods/pm-project/main.js` | `[@mods/pm-project/main.js](file:mods/pm-project/main.js)` |

Why `[@Label](scheme:target)` beats custom XML tags or sideband JSON fields:

1. **Zero schema churn in the event log**: the exact string sent into the terminal is recorded in `conversation.jsonl` by the turn hook, so optimistic pending-bubble matching, remote-machine delivery, raw terminal reading, and optional Discord mirroring all stay human-readable without changing log formats.
2. **Self-explanatory and token-frugal for any coding agent**: Claude Code, Codex, pi, and others parse `thread:<id>`, `library:project/...`, and `file:...` naturally. For `library:` links, a short path-resolution footer can be appended on delivery (e.g. `[refs] library:project/spec-worker-alerts.md -> ~/.claude/pm/projects/<slug>/spec-worker-alerts.md`) so the manager can copy the resolved path straight into a brief without cluttering the visible message body.
3. **Symmetric rendering in bubbles**:
   - Manager replies already emit `[Title](thread:<id>)` links that open the thread pane on click;
   - Extending the link handler to `library:<root>/<path>` (opens the item in Library), `session:<terminal>` (focuses/peeks that terminal), and `file:<path>` (shows full path on hover or previews) makes every reference interactive;
   - Sent user bubbles render all four `[@...](scheme:...)` patterns as read-only clickable chips matching the input box.

### 3.4 Post-Send Routing and Manager Playbook Conventions

1. **Main project input (`say`)**: always sends to the project's manager terminal. Add three rules to `mods/pm-dash/skill/references/pm-playbook.md`:
   - Message contains `[@...](thread:<id>)` with **nudge / revision / steer** intent → run `pm.py update <id> --status in_progress --note "<distilled instruction>" --send` (`pm.py reattach <id>` first if offline).
   - Message contains `[@...](thread:<id>)` asking for **status or dispatching new work from its findings** → read that task's ledger report or research README and pass the relevant context into the new task's brief.
   - Message contains `[@...](library:...)` or `[@...](file:...)` → pass the path straight into the worker brief rather than reading large files in the manager session; if the user asked to edit or delete a memory entry, invoke `pm.py remember` / `forget` directly.
2. **Thread detail input (`say-thread`)**: always sends to that thread's active worker terminal so users inspecting a thread can hand extra references straight to its worker.

### 3.5 Suggested Implementation Steps

1. **Backend & skill updates**:
   - Document `thread:` / `library:` / `file:` / `session:` handling in `pm-playbook.md`;
   - Teach the prompt-submit hook (or frontend send helper) to append resolved file paths for `library:<root>/<path>` references without mutating the user message stored in `conversation.jsonl`.
2. **`mods/pm-project` UI**:
   - Add pure functions + unit tests in `model.js`: `@` trigger detection, three-source candidate builder and fuzzy ranker, two new `Esc`-stack levels, extended link parser, and draft `tokens` serialization;
   - Update `main.js`: prefetch Library metadata and `git ls-files` on project open or first `@`; render the two-level `Popup` menu and key bindings; wire `replace_range_with_token` + `Textarea.token()`; render clickable chips across user and manager bubbles;
   - Verify visually across level-1 menu, level-2 submenu, global search, inline input chips, and sent bubble navigation.

## 4. Decisions Made

| Question | Decision | Rejected alternatives |
| --- | --- | --- |
| Who receives a message containing `@thread` in the main input box? | **The manager receives it; `@` is an ID-carrying reference pointer** (matching Cursor Projects; use `say-thread` in the thread pane for direct 1:1 worker input). | Sending straight to the `@`-mentioned worker terminal (breaks on multiple `@`s or offline/merged threads and bypasses `in_progress` stall tracking); adding a routing toggle (gives one chip two conflicting behaviors). |
| Which categories ship in v1 of the `@` menu? | **Three: `Threads`, `Library`, `Files`**, with active threads and recent docs shown flat below the level-1 divider. | `Threads` + `Library` only (misses repo file scoping in main chat); splitting standalone sessions into a fourth `Agents` category (often 0–2 items, leading to empty submenus). |
| How do selections appear in the input box? | **Inline chips inside the text + clickable chips in sent bubbles** (preserving natural phrasing like `"update @main.js per @cursor-research"`; falls back to plain `@Name` text in the editor if CJK IME hits token issues while still rendering bubble chips). | Top attachment strip above the input box (simpler, but loses inline grammatical relationships between multiple `@` references). |
